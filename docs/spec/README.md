# docs/spec ― 要件定義書／仕様書

> **位置づけ:** 実装すると決めたアイデアの**要件定義書＝仕様書**を管理する。実装（`projects/`）の拠り所となる「正」のドキュメント。
> 「なぜやるか・やる価値があるか」は `docs/ideas/`、本フォルダは**何をどこまで作るか**を扱う。

---

## バージョン管理の規約（SES_sales と同じ）
仕様の版は **Git（履歴）** に加え、各ファイルの**フロントマターの `version` とステータス**、および**改訂履歴表**で明示管理する。

### フロントマター
```
---
doc_id: SPEC-001                 # 仕様書の一意ID（連番）
title: 〇〇ツール 要件定義
version: 0.1                     # セマンティック版（下記ルール）
status: ドラフト                 # ドラフト / レビュー中 / 確定 / 改訂中 / 廃止
最終更新: 2026-10-06
owner: 富田
idea: docs/ideas/IDEA-0001_xxx.md
project: projects/xxx/
---
```

### バージョン番号ルール
- `0.x` … ドラフト（確定前）。試作中はここでよい。
- `1.0` … 初回**確定**（実装の基準として承認された版）。
- `x.Y`（マイナー）… 後方互換の追記・明確化。
- `X.0`（メジャー）… 仕様の方針転換・破壊的変更。

### ステータスの遷移
`ドラフト → レビュー中 → 確定(vX.0) → 改訂中 → （再）確定`

### 推奨する章立て
1. 位置づけ（紐づくアイデア・解く課題） 2. 目的・スコープ（やらないことも書く） 3. 利用者と利用シーン 4. 機能要件 5. データ・外部連携 6. 非機能要件（コスト・実行頻度・秘密情報の扱い） 7. 未決事項 8. 改訂履歴

### 改訂履歴
各仕様書の末尾に `## 改訂履歴` 表（版・日付・変更内容・担当）を持つ。構造を伴う重要な版上げは、リポジトリ直下の `変更履歴.md` にも記録する。

## ファイル命名
- `docs/spec/<対象システム名>_spec.md`（版はファイル名に含めず、frontmatterで管理）。
